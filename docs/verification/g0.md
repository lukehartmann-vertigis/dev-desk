### Compatibility findings and deliberate adjustments

- TypeScript 7.0.2 was outside typescript-eslint's supported peer range. The
  fixture pins TypeScript 5.9.3 rather than overriding that peer constraint.
- The aggregate Next ESLint preset brought plugins incompatible with ESLint 10.
  ESLint 9.39.5 was reported unsupported. The fixture therefore uses supported
  ESLint 10 with direct Next, React Hooks, and TypeScript presets, not a forced
  aggregate-preset installation. This does not establish full application
  accessibility coverage.
- `skipLibCheck` is enabled because Drizzle's declarations include missing
  optional database drivers and incompatible declarations for unused dialects.
  Owned source and its use of imported APIs remain strictly checked; this is not
  a claim that all third-party declarations typecheck.
- Two narrowly scoped npm overrides address actual audit findings:
  SDK Zod resolves to the direct Zod 4.6.6 dependency
  (`GHSA-mrhx-c7xc-m3w5`), and esbuild-kit core-utils uses esbuild 0.25.12
  (`GHSA-67mh-4wv8-2f99`). Drizzle migration generation and SDK schema/tool
  registration and dispatch were exercised with these overrides.
- Drizzle Kit still brings deprecated esbuild-kit packages. Do not add a
  dependency on them; reassess the overrides during upgrades.
- The final image passes `npm ls --include=dev --all` and
  `npm audit --include=dev --include=optional --audit-level=low` with **zero
  reported vulnerabilities**. This is a registry-audit result, not a security
  certification.
- Clean image installation uses `npm ci --ignore-scripts`. Shipped artifacts
  suffice on the tested Linux x86_64 image; other architectures are not certified.

## 3. Production lifecycle evidence

The historical fixture Dockerfile used a regular build rather than
assuming standalone tracing includes native/SDK assets. It copied the complete
fixture dependency tree, including development tools for verification; this is
not a production-image size or hardening prescription.

The build sets a forbidden runtime database path and asserts that its directory
was not created. Next.js compilation, static generation with five workers, and
the build typecheck completed without creating that database.

The serving image runs `next start` as UID 1000, with a dedicated SQLite volume
and loopback-only published port. Startup instrumentation owns one process-global
resource shared across entry bundles; a route cannot silently create a replacement
coordinator if instrumentation is missing.

Observed evidence:

- First coordinator: `79dfdcd9-f702-4b77-b091-226f1771dbb3`, PID 7, UID 1000.
- With no browser open, the durable counter increased from 719 to 723 while the
  coordinator identity stayed unchanged.
- Two browser tabs and twenty concurrent status reads reported one coordinator
  and one active boot. Status responses explicitly used `no-store`.
- Four concurrent manual refreshes returned one cycle ID, with at least three
  requests joining the existing cycle.
- SIGTERM recorded a shutdown marker at `2026-10-26T14:37:18.302Z` and closed
  SQLite. The container exited with the expected SIGTERM status 143, not a forced
  kill.
- A new container on the same volume started coordinator
  `b0c30694-27bf-4053-b06c-fe0c38eb4740`. The prior boot retained its shutdown
  marker, exactly one boot was active, and the persisted counter advanced beyond
  723. A subsequent stop recorded the second shutdown marker too.

The synthetic work/delay values are 100/250 milliseconds, not the product's
180-second polling policy. No live ADO synchronization, scope replacement,
upstream cancellation, crash recovery, or multi-replica behavior is established.
Repeat lifecycle checks after changing Next.js, deployment mode, or process
ownership. [ADR-0004](../adr/0004-background-sync.md) is accepted only for the
verified single-replica, long-lived Node hosting model.

A read-only database inspection still needed a sidecar-writable volume for WAL
access; a wholly read-only mount initially failed. Backup/restore acceptance must
use the documented stopped-app, complete-storage procedure, not assume that a
bare read-only WAL query proves backup usability.

## 4. SDK evidence and boundary

The historical SDK probe passed seven explicit checks in
the fixture's final non-root production image with networking disabled:

1. Start the bundled runtime, ping it, and confirm unauthenticated status with
   ambient login disabled.
2. Put a literal synthetic ADO canary in the parent environment and confirm that
   the managed child's environment contains neither that variable nor its value.
3. Create a durable named synthetic session without an LLM request.
4. Dispatch the configured synthetic tool through the native tool pipeline and
   check its actual result.
5. Verify that the exact initialized tool list is only `g0_read` on create and
   resume, and that attempting `bash` returns an explicit missing-tool failure.
6. Stop and restart the managed runtime, then resume the same session with its
   tool policy reapplied.
7. Delete the session, stop the runtime, verify that session-ID directories are
   gone, restart again, and verify that the session list still excludes it.

The only prompt-free tool is the fixed, side-effect-free synthetic marker tool.
Other permission requests are rejected. The initial deny-all callback also
rejected that custom tool until this exact exception was declared. Future
application handlers still require independent scope, revision, retry, intent,
and deletion checks; this fixture does not supply those checks.

Native tool RPC errors can resolve as a structured non-success result rather
than reject the JavaScript promise. A fulfilled promise is not sufficient evidence
of successful tool execution.

No host login, existing Copilot state, ADO credentials, or real conversations were
used. No model prompt was sent. Session state was isolated and cleaned up.
The child-environment check is not an OS sandbox or protection against a
compromised same-UID native process. API tool filtering and credential inheritance
must not be described as filesystem/process isolation.

Still required before the SDK gate can pass:

- Explicit supported GitHub authentication, selected-model access, and a real
  synthetic model turn.
- Representative/adversarial intent cases and read/clarify tool restrictions.
- Application run cancellation, total budget, tool-call limits, and exact
  deletion approval enforcement.
- Provider-driven callback/retry identities and application receipt safety.
- Real transcript continuation after container replacement with SDK state on the
  persistent volume, plus complete app/SDK clearing and interrupted-cleanup cases.

## 5. Azure DevOps evidence and blockers

Existing authenticated MCP metadata established the Utilities project, selected
repository UUIDs, two teams, and their settings. It does not establish the
application PAT's identity, scopes, access, or all relevant group memberships.
No new work-item content, PR discussions, or source code was read in this G0 step.

Official API contracts were checked:

- [Graph memberships](https://learn.microsoft.com/en-us/rest/api/azure/devops/graph/memberships/list?view=azure-devops-rest-7.1)
  uses `7.1-preview.1`, supports only `depth=1`, and documents `vso.graph`.
  Nested ancestry requires explicit traversal with cycle/duplicate protection.
- [PR reviewers](https://learn.microsoft.com/en-us/rest/api/azure/devops/git/pull-request-reviewers/list?view=azure-devops-rest-7.1)
  documents positive votes 5/10, reviewer descriptors, and `votedFor` group-vote
  roll-up. Those fields do not by themselves prove complete user membership.

An explicitly provisioned, read-only application test credential is still needed.
Test PAT identity, both selected repositories, descriptor/reviewer mapping,
nested and directory-backed membership, insufficient permissions, pagination,
and complete versus incomplete review results. Continue to report incomplete
data rather than silently dropping group requests.

Do not extract credentials from MCP or borrow VS Code login. Do not paste tokens
into chat, commit them, or include them in logs/reports. Arrange a local,
explicitly scoped live-test credential setup before adding live probes.
